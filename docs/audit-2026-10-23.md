# Audit sécurité et propreté de Zenytt — 23 octobre 2026

Périmètre :
- application de bureau : backend Tauri/Rust, crates `core`, `profiles`, `mcp`, `ai`, `agent` ;
- nouveautés de la version 1.2.0 : profils SFTP seul et FTP/FTPS, page Système et API des hébergeurs, application compagnon mobile ;
- serveur `zenytt-sync`, bot Discord, CI et chaîne de publication ;
- alertes GitHub ouvertes (Dependabot, CodeQL).

Méthode :
1. Quatre audits parallèles, un par surface :
   - identité, secrets et cryptographie ;
   - commandes exécutées à distance ;
   - application, IPC et rendu ;
   - composants serveur et chaîne d'approvisionnement.
2. Deux audits de propreté : Rust et TypeScript.
3. Correction par lots, chacun avec un test qui reproduit l'attaque ou le défaut.
4. Revue finale indépendante.

Les audits précédents (`audit-2026-09-21.md`, `audit-2026-09-26*.md`) ont été relus d'abord : aucune régression de leurs correctifs n'a été trouvée.

**Verdict global** : les fondations restent saines. Comme en septembre, les failles venaient d'**hypothèses de confiance trop larges** :
- le stockage de synchronisation était cru sur parole ;
- l'assistant IA décidait seul à partir d'une liste noire ;
- n'importe quel tag publiait une mise à jour signée.

Niveaux : 🔴 critique · 🟠 élevé · 🟡 moyen · ⚪ faible / à décider.

## Détail des points principaux

### 1. 🔴 Synchro : enveloppe non chiffrée acceptée
`export::open()` renvoyait le contenu d'une enveloppe `"encrypted": false` sans jamais utiliser la phrase de passe. Quiconque pouvait écrire dans le stockage pouvait donc injecter des données. Cela vise l'hôte de `zenytt-sync`, un VPS compromis ou le dossier OneDrive/Dropbox en mode fichier. Les données injectées pouvaient changer l'hôte d'un serveur, pré-approuver la clé d'hôte de l'attaquant et réécrire les snippets. À la connexion suivante, le mot de passe partait chez l'attaquant sans demande d'approbation.

**Correctif** : la synchro passe par `open_sync`, qui refuse toute enveloppe non chiffrée et toute phrase de passe vide.

### 6. 🟡 Synchro : rejeu et retour en arrière
Le numéro de révision n'était pas authentifié. **Correctif** :
- La révision est liée au chiffrement : les données authentifiées incluent `format#rev=N`.
- Le client refuse une révision inférieure à la dernière vue, et une révision égale dont le contenu diffère (empreinte `last_remote`).
- Un stockage vidé arrête la synchro au lieu de repartir de zéro.
- Un contenu au format 1 n'est que fusionné, jamais appliqué tel quel.

**Conséquence** : le format passe en version 2. Les versions antérieures à 1.2.0 refusent ce format, sans rien abîmer.

**Limite** : un stockage hostile peut encore figer la synchro, ou montrer des historiques différents à deux appareils. Il ne peut plus revenir en arrière ni injecter de contenu.

### 2. 🟠 Verrou contourné au redémarrage
`LOCKED` démarrait à `false`. **Correctif** :
- Le verrou est engagé dès la première instruction de `setup`.
- L'interface n'hydrate rien avant le déverrouillage : serveurs, espace de travail, connexion automatique et synchro attendent.

### 3. 🟠 Assistant IA en mode Auto
Seule une liste noire décidait d'une exécution sans confirmation. Une instruction cachée dans des journaux de conteneur pouvait donc faire lancer `bash -c "$(curl …)"` en root.

**Correctif** : une liste blanche (`auto_safe`).
- Une commande ne s'exécute seule que si chaque segment est une lecture connue, avec ses options vérifiées : `find` sans `-exec`/`-delete`, `systemctl status`, `docker logs` sans `-f`, etc.
- Elle ne doit contenir aucune substitution, redirection ou variable.
- Tout le reste demande confirmation. 71 cas sont testés.
- Dans l'interface, la commande proposée passe à la ligne, et un badge signale les commandes enchaînées.

**Risque restant** : les lectures autorisées tournent en root, et la sortie n'est masquée que par heuristique avant d'aller au fournisseur.

### 4. 🟠 Publication des mises à jour
**Correctif dans le dépôt** :
- Les jobs `build`, `sign-windows` et `publish` passent par l'environnement GitHub `release`.
- La signature utilise la CLI Tauri fixée dans le lockfile, au lieu d'un `npx` résolu à la volée.
- Le bot ne demande plus que `Issues: Read and write` sur le dépôt Zenytt. Ses captures vont dans un dépôt séparé, avec un jeton dédié (`GITHUB_ATTACHMENTS_REPO`, `GITHUB_ATTACHMENTS_TOKEN`).

**À configurer sur GitHub** :
1. Créer l'environnement `release` avec un validateur obligatoire, limité aux tags `v*`.
2. Y déplacer les secrets de signature : `TAURI_SIGNING_PRIVATE_KEY`, son mot de passe et les `SIGNPATH_*`.
3. Créer une règle de tags `v*` réservée aux admins.
4. Réduire le jeton du bot sur le dépôt Zenytt à `Issues: Read and write`, et le renouveler s'il a déjà eu un accès en écriture au contenu.

### 5. 🟠 Amorce sudo falsifiable
Le mot de passe sudo enregistré était tapé dès qu'un marqueur fixe apparaissait dans la sortie. Ce marqueur était émis même quand sudo n'en avait pas besoin. Une VM, sur sa console série, ou un conteneur, via son `.bashrc`, pouvait donc l'obtenir.

**Correctif** :
- Le marqueur porte un nonce aléatoire propre à chaque onglet (122 bits).
- Le chemin « pas nécessaire » émet un marqueur qui désarme immédiatement.
- Un mot de passe contenant des caractères de contrôle n'est jamais tapé.

### 8. 🟡 Noms de bases MySQL
Les noms viennent de `SHOW DATABASES` et sont donc contrôlés par le serveur, alors qu'ils étaient insérés tels quels dans `sh -c`.

**Correctif** :
- Un nom qui commence par `-` ou contient `$` est refusé.
- `shell_quote` est appliqué à chaque nom.
- Le mot de passe passe par `MYSQL_PWD` au lieu de la ligne de commande.

## Propreté du code

Le code était déjà propre :
- aucun avertissement `dead_code` ;
- aucune dépendance inutile ;
- aucun TODO ni code commenté ;
- commentaires en français.

Changements :
- **Rust** : une seule fonction `err()` au lieu de 14 copies ; `section()` fusionnée ; 9 fonctions nginx et 3 commandes Tauri inutilisées supprimées ; une copie de tampon en moins par paquet de terminal partagé ; commentaires `shortcut:` regroupés.
- **TypeScript** : fonctions d'appel mortes supprimées ; deux scrutations manuelles passées sur `usePolling` ; trois formateurs « il y a » remplacés par un seul `formatAgo` ; `export` superflus retirés ; plugin presse-papiers mobile inutilisé supprimé.
- **Synchro** : le transport HTTP, copié entre le bureau et le mobile, est mutualisé dans `zenytt-profiles`.

## Points ouverts

| Point | Option |
|---|---|
| Relais : l'hôte d'une session de partage n'a besoin que de l'identifiant | Faire renvoyer un secret d'hôte par `POST /v1/relay` et l'exiger à la connexion (changement client et serveur) |
